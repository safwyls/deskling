Inside the firmware

One firmware per companion

Each pet is a PlatformIO environment. They share every line of code; what differs is a few build flags and a folder of frames.

[env:crumb]
build_flags = ${env.build_flags} -DPET_CRUMB -DPET_ID=\"crumb\" -DPET_NAME=\"Crumb\"
build_src_filter = ${env.build_src_filter} +<anims/crumb/>
  • src/anims/<pet>/ holds that pet’s loops as generated C files with the same names (pet_walk, pet_happy…), so the code never knows which pet it is. A pet without a clip for something gets a stand-in in stand_ins.cpp (Crumb’s Stretch borrows his bounce until a proper clip exists).
  • include/theme.h gives each pet its colours: screens, clock faces, the LED ring at rest, and the setup page (as CSS variables). The four need colours are shared, because they mean the same thing on every pet.
  • PET_NAME goes into every sentence on screen (“Sprig is asleep”), and the dial tells the phone app which pet it is, so the app shows the same one.

Wisp’s firmware is 11.9 MB, Sprig’s 9.6 MB and Crumb’s 8.0 MB, almost all of it animation. The partition table gives the app 14 MB of the 16 MB flash, which is why each pet is its own firmware: two sets of frames don’t fit.

Memory: the real constraint

The ESP32-S3 has two kinds of RAM. Internal RAM is fast but small, a few hundred kilobytes, and it’s the only kind the Wi-Fi and Bluetooth drivers can use. PSRAM is 8 MB, slower, and fine for almost everything else. Most of the hard bugs came from running out of the first.

  • LVGL’s heap lives in PSRAM (a custom allocator in lv_mem_psram.c), and decoded frames go into a 2 MB PSRAM cache.
  • One small render buffer of 30 lines stays in internal RAM, because the display’s DMA needs it there.
  • Bluetooth takes about 75 KB of internal RAM; the dial’s own setup network takes about 40 KB more. They don’t fit together, so Bluetooth pauses while the setup network is up and comes back after.
  • An early version also talked to Home Assistant; dropping it freed about 40 KB, which is what made room for Bluetooth.

The setup network used to crash the dial outright: the Wi-Fi driver doesn’t fail gracefully when internal RAM runs out. The crash-report QR code on Settings > Last restart is how that was found, decoded against the build’s .elf with xtensa-esp32s3-elf-addr2line.

Animation on a microcontroller

Every loop is stored as 8-bit indexed images with a transparent palette: one 256-colour palette shared by all frames of a loop, so colours don’t flicker from frame to frame. That’s half the size of 16-bit colour, transparent (so the clock can sit behind the pet), and measured at about 40 dB against the source. The ground shadow is baked in. The bubble’s position is stored per frame so it floats with the pet’s face. Clips to dial frames covers how the frames are made.

Talking to the phone

The app and the dial speak one small JSON protocol, over HTTP on Wi-Fi (POST /api, the phone’s key in a header) or over Bluetooth (one message per line on a custom service). Pairing trades the 6-digit code on the dial’s screen for a random key. The dial is the source of truth: the phone sends what it logged, with the time it happened, and takes the dial’s state back.

For instant sync the phone keeps a Bluetooth connection open while nearby. The dial watches a counter that moves on every action and, when it changes, sends {"event":"changed"}; the phone syncs at once. Replies always carry "ok" and events never do, which is how the phone tells them apart.

Settings in flash

Settings use Arduino’s Preferences on ESP-IDF’s NVS, one key each: ssid, pass, rem_water…rem_move, h_start, h_end, tz, clock, clock_st, post, sit, stand and the rest. That’s what lets the firmware page hand a freshly flashed dial your settings: it builds the NVS partition in the browser (site/js/nvs.js) and writes it at 0x9000.
